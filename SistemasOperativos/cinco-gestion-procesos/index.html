🧩 ¿Qué es un proceso?

⏱️ 45 minutos · "Un programa que cobra vida" — la unidad de trabajo del SO

🧠 La idea central

Un programa es un archivo en el disco: código muerto, inerte, esperando. Un proceso es ese programa en ejecución: vive en la RAM, consume CPU, tiene un PID (identificador único) y el SO lo vigila. Es la diferencia entre una receta en un libro (programa) y alguien cocinando con esa receta (proceso). Si abres el mismo programa dos veces, tienes dos procesos distintos, cada uno con su propio PID.

🔄 Actividad en pareja — 3 minutos

Abran una terminal (o el Administrador de tareas con Ctrl+Shift+Esc). Escriban ps aux en Linux/macOS o miren la pestaña "Detalles" en Windows. ¿Cuántos procesos hay activos? Anoten el número. Sí, son muchos más de los programas que abriste: el SO corre decenas de procesos en segundo plano sin que te des cuenta.

🔍 La anatomía de un proceso

Cada proceso, por pequeño que sea, tiene estos componentes en memoria. El SO le asigna y vigila cada uno.

🗂️ Segmento de código

Las instrucciones del programa (solo lectura). Es el "qué hacer". Si dos procesos abren el mismo programa, pueden compartir este segmento.

📊 Segmento de datos

Las variables globales y estáticas. Se modifica durante la ejecución. Es el "estado actual" del programa.

📚 Stack (pila)

Las variables locales y las llamadas a funciones. Crece y se encoge con cada función que entra y sale. Sin esto, no hay recursión.

📦 Heap (montículo)

La memoria dinámica (malloc, new). Se pide y se libera a mano. Si se olvida liberar: fuga de memoria.

🆔 PCB (Process Control Block)

La "ficha" del proceso: PID, estado, registros de la CPU, memoria asignada, archivos abiertos. El SO guarda aquí todo lo que necesita para retomarlo.

💡 ¿Qué es el PCB?

El PCB (Process Control Block) es la tarjeta de identidad del proceso. Cuando el SO pausa un proceso para darle la CPU a otro, guarda el estado de la CPU (registros, contador de programa) en el PCB. Cuando vuelve a darle la CPU, restaura ese estado y el proceso continúa como si nada. A este cambio se le llama context switch (cambio de contexto), y es la magia que permite la multitarea.

💻 Procesos en una terminal real

En Linux/macOS puedes ver tus procesos con estos comandos. Pruébalos si tienes una terminal a mano:

terminal — ps
$ ps                # procesos de esta terminal
$ ps aux            # todos los procesos del sistema
$ top               # procesos en tiempo real (tecla q para salir)
$ htop              # top mejorado (si está instalado)
$ pstree            # árbol: muestra qué proceso creó a cuál
$ pidof firefox     # ¿cuál es el PID de firefox?

🌳 Procesos padre e hijo: el árbol de procesos

Cuando un proceso crea a otro, se llama fork (bifurcación). El creador es el padre; el nuevo es el hijo. Así se forma un árbol de procesos con un único ancestro: en Linux es systemd (PID 1), en Windows es System. El comando pstree lo muestra.

⚠️ Error común: "no pasa nada si un hijo queda huérfano"

Si el padre termina antes que el hijo, este queda huérfano y lo adopta init/systemd (PID 1). No es un error fatal en Linux, pero en programas mal escritos puede generar procesos zombi: hijos que ya terminaron pero el padre no recogió su estado. Se quedan ocupando una entrada en la tabla de procesos. Por eso un SO bien administrado vigila y limpia los zombis.

🔄 Ciclo de vida de un proceso

⏱️ 50 minutos · "Nace, espera, corre, muere" — los 5 estados

🧠 La idea central

Un proceso no aparece y desaparece: pasa por estados bien definidos. El SO lo va moviendo entre ellos según la disponibilidad de la CPU y los recursos. Entender estos estados y sus transiciones es entender cómo el SO logra la ilusión de que "todo corre a la vez" cuando en realidad rota la CPU entre procesos a velocidad de relámpago.

💡 ¿Qué es el cambio de contexto?

Cuando el SO quita la CPU a un proceso y se la da a otro, hace un context switch: guarda el estado del proceso saliente en su PCB y carga el estado del proceso entrante desde su PCB. No es gratis: cuesta microsegundos de CPU. Por eso un SO con demasiados procesos activos puede gastar más tiempo cambiando contexto que ejecutando trabajo real. A eso se le llama thrashing.

⚠️ Error común: confundir "bloqueado" con "terminado"

Un proceso bloqueado sigue vivo, solo está esperando un recurso (un click, un archivo, la red). Volverá a estar listo cuando el recurso llegue. Un proceso terminado se va para siempre: libera su memoria y su PCB se recoge. Si confundes ambos, no entenderás por qué un programa "se queda pensando" (bloqueado) vs "se cerró" (terminado).

📅 Planificación de procesos

⏱️ 50 minutos · "El scheduler decide quién corre y cuánto" — algoritmos

🧠 La idea central

Hay muchos procesos listos pero solo una (o pocas) CPU. ¿Quién decide quién corre primero? El scheduler (planificador), una parte del kernel. Usa algoritmos con criterios distintos: equidad, eficiencia, respuesta rápida. Entenderlos es entender por qué a veces tu PC "se siente lenta" aunque la CPU no esté al 100%.

💡 ¿Qué es el quantum?

En Round Robin, cada proceso recibe la CPU por un tiempo fijo llamado quantum (ej. 2 ms). Si no terminó, vuelve a la cola de listos y le toca al siguiente. El tamaño del quantum es clave: muy corto → demasiados context switches (lento); muy largo → parece FCFS (injusto). Linux usa CFS (Completely Fair Scheduler), una variante moderna que garantiza equidad proporcional.

⚠️ El problema de la inanición (starvation)

En SJF y en Prioridad, un proceso puede quedarse esperando para siempre si siempre llegan procesos más cortos o de mayor prioridad. A eso se le llama inanición. La solución es el aging (envejecimiento): a medida que un proceso lleva mucho tiempo esperando, el SO le sube la prioridad hasta que corra. Sin aging, SJF puede ser injusto.

💬 Comunicación entre procesos (IPC)

⏱️ 45 minutos · "Los procesos hablan entre sí" — pipes, señales, sockets

🧠 La idea central

Cada proceso tiene su propia memoria privada: uno no puede leer la RAM del otro (eso es bueno, es aislamiento). Pero a veces necesitan coordinarse: un proceso produce datos, otro los consume; un proceso le avisa a otro que terminó. Para eso existen los mecanismos de IPC (Inter-Process Communication). Son las "tuberías" y "señales" por las que los procesos se hablan sin romper el aislamiento.

🔄 Actividad en pareja — 2 minutos

Piensen en una cocina de restaurante: el mesero anota el pedido, lo pone en un tablero; el cocinero lo lee, prepara el plato y toca una campanilla para avisar. ¿Cuál es el "mecanismo de comunicación" entre mesero y cocinero? Escríbanlo. Esa intuición es exactamente un pipe (el tablero) y una señal (la campanilla).

💡 Pipes en la terminal

Ya usaste pipes sin saberlo. Cuando escribes ls | grep pdf, la | es un pipe: conecta la salida de ls con la entrada de grep. El SO crea un pipe, lanza ambos procesos y los conecta. Por eso ls "produce" y grep "consume". Es IPC en acción, en una sola línea de terminal. 🔗

⚡ Señales: interrupciones entre procesos

Una señal es una notificación corta que un proceso le envía a otro. No transporta datos (solo un número), pero hace que el receptor reaccione. Las más conocidas:

🛑 SIGINT (2)

La señal de Ctrl+C. Le dice al proceso "termina ya". Es la forma educada de detener un programa. Si no la maneja, muere.

☠️ SIGKILL (9)

La señal inatratable. kill -9 PID. El kernel mata el proceso al instante; no puede ignorarla ni limpiar. Úsala solo en emergencia.

📞 SIGTERM (15)

La señal "por favor termina". kill PID sin número envía esta. El proceso puede capturarla, guardar su trabajo y salir limpiamente. Es la señal recomendada.

🔄 SIGHUP (1)

Originalmente "colgó el terminal". Hoy se usa para pedir a un demonio que recargue su configuración sin reiniciar. Muy útil en servidores.

💻 Comandos IPC reales

terminal — ipc
# Pipe entre dos comandos:
$ ls -l | grep ".pdf" | wc -l

# Enviar una señal (SIGTERM por defecto):
$ kill 1234

# Forzar la muerte (SIGKILL):
$ kill -9 1234

# Ver señales disponibles:
$ kill -l

# IPC con nombre: named pipe (FIFO)
$ mkfifo /tmp/micanal
$ echo "hola" > /tmp/micanal &
$ cat /tmp/micanal

⚠️ Error común: usar kill -9 por costumbre

Mucha gente mata procesos con kill -9 (SIGKILL) porque "es lo que funciona". Pero SIGKILL no permite limpieza: el proceso no puede cerrar archivos, liberar locks ni guardar su estado. Es como apagar el PC del botón. Siempre intenta primero kill (SIGTERM). Si tras 5-10 segundos no muere, entonces sí kill -9. El orden importa.
