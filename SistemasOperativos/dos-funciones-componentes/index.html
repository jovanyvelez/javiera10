⚙️ Gestión de procesos

⏱️ 35 minutos · "El director de orquesta de la CPU"

🦹 El villano: el lag en los juegos

Estás jugando Valorant y a la vez tienes Twitch abierto. De pronto el juego se "congela" medio segundo y mueres. ¿Culpa de tu internet? No siempre. Muchas veces es la CPU que no da abasto: el SO no logra repartir el procesador entre el juego, Twitch, Discord y Chrome. Ese "tartamudeo" es el planificador luchando.

🧠 La idea central

Un programa es la receta escrita (código en disco). Un proceso es el chef cocinando esa receta, vivo, usando CPU y memoria. Cuando abres WhatsApp, el programa pasa a ser proceso: adquiere un PID, un estado y un turno para la CPU. El planificador (scheduler) decide quién corre cuándo y por cuánto (el quantum).

🔄 Actividad en pareja — 2 minutos

Abran 3 apps en su PC. ¿Cómo hace el SO para que las tres parezcan funcionar a la vez con una sola CPU? Discutan 1 minuto y escriban su hipótesis.

👨‍🏫 En el aula — Admin de Tareas en la TV

💡 ¿Qué es el cambio de contexto?

Al sacar a un proceso de la CPU y meter a otro, el SO guarda el estado del primero (registros, contador) y carga el del segundo. Como marcar el libro donde vas leyendo antes de cambiar de lectura. Tiene un costo: unos microsegundos "perdidos".

🔍 En la vida real: Windows vs Linux vs Android

Windows usa un planificador por prioridades (las apps en primer plano tienen más). Linux usa CFS (Completely Fair Scheduler) que reparte la CPU de forma justa. Android hereda el kernel de Linux (CFS), pero encima prioriza agresivamente la app en pantalla y "congela" las de fondo para ahorrar batería.

💾 Gestión de memoria

⏱️ 35 minutos · "El escritorio compartido" — RAM, páginas y swap

🦹 El villano: "Out of Memory" y Chrome devorando RAM

Estás jugando Minecraft y de pronto se cierra solo con un cartel rojo: Out of Memory. O abres la pestaña 47 de Chrome y la laptop grita pidiendo cerrar cosas. No es mala suerte: la RAM se llenó y el SO no supo dónde más meter cosas. Veamos qué hace la memoria y por qué se agota.

🧠 La idea central

La RAM es el "escritorio" donde los procesos ponen lo que usan ahora. Rápida pero pequeña (4–16 GB) y se borra al apagar. El disco es la "bodega": lento, enorme, permanente. El SO reparte la RAM entre procesos y, cuando se llena, usa la memoria virtual: mueve páginas poco usadas al disco (swap) para hacer sitio.

🔄 Actividad en pareja — 2 minutos

Si la RAM es el escritorio y el disco es la bodega: ¿qué hace el SO cuando el escritorio se llena de papeles y necesitas otro? ¿Los tiras o los llevas temporalmente a la bodega? Discutan. Esa analogía es exactamente el swap.

📦 Paginación: la RAM en "marcos"

El SO divide la RAM en marcos del mismo tamaño (ej. 4 KB) y la memoria de cada proceso en páginas del mismo tamaño. Una página puede ir a cualquier marco libre.

📄 Página

Trozo de memoria lógica de un proceso. Todas del mismo tamaño. El proceso las ve seguidas, aunque físicamente estén dispersas.

🗄️ Marco

Hueco de la RAM física, del mismo tamaño que una página. El SO mapea páginas → marcos.

🔄 Swap

Cuando la RAM se llena, el SO mueve páginas poco usadas al disco. Es lento, pero evita que el sistema se caiga.

👨‍🏫 En el aula — Midan su RAM real

  1. Anoten cuánta RAM libre les queda (en GB o %).

⚠️ El swap es lento

Cuando tu PC "se pone lenta" con muchas apps, suele ser porque el SO está swapping mucho: pasando páginas del disco a RAM. El disco es ~1000× más lento que la RAM. Por eso tener más RAM mejora la velocidad más que tener un CPU más rápido.

🔍 En la vida real: Windows vs Linux vs Android

Los tres usan paginación y memoria virtual. Windows usa un archivo pagefile.sys. Linux usa una partición swap (más eficiente). Android no hace swap tradicional: cuando la RAM se llena, mata directamente las apps en segundo plano y las reinicia al volver. Por eso tu app de fondo "se reinicia" en Android en lugar de quedarse lenta.

🗄️ Gestión de almacenamiento

⏱️ 30 minutos · "El archivador organizado" — archivos, carpetas y rutas

🦹 El villano: "No tienes permisos de administrador"

Intentas borrar un archivo viejo y aparece el molesto cartel: "No tienes permisos de administrador para realizar esta acción". ¿Por qué el SO te bloquea si es tu computadora? Porque no eres el "dueño" de ese archivo, o porque está marcado como de solo lectura. El sistema de archivos no es solo carpetas: también es quién puede tocar qué.

🧠 La idea central

El disco guarda todo: el SO, las apps, tus fotos. Sin organización sería un caos. El SO lo resuelve con un sistema de archivos: una estructura de carpetas y archivos en forma de árbol. Cada archivo tiene una ruta que dice cómo llegar a él desde la raíz.

💡 Archivos vs carpetas

Un archivo guarda datos (foto, documento, canción). Una carpeta es un contenedor que organiza archivos y otras carpetas. La extensión (.jpg, .mp4) le dice al SO qué app lo abre.

🔍 En la vida real: NTFS vs ext4 vs almacenamiento Android

Windows usa NTFS: permisos, cifrado y recuperación. Linux usa ext4: robusto y open source. Android da a cada app su carpeta aislada (/data/data/<app>): una app no puede tocar los datos de otra. Ese aislamiento es seguridad.

🔌 Drivers y dispositivos

⏱️ 25 minutos · "El traductor del hardware" — I/O y controladores

🦹 El villano: el mouse RGB que no prende

Compraste un mouse gamer nuevo con luces RGB y 12 botones. Lo conectas y... las luces no prenden y los botones extra no funcionan. El mouse básico sí mueve el cursor. ¿Magia? No: el SO sabe lo que es un "mouse genérico", pero no sabe qué hacer con las luces ni los botones extra. Necesita el driver: el manual del fabricante.

🧠 La idea central

El SO habla con cientos de dispositivos distintos: teclado, pantalla, impresora, cámara, disco, red. No puede saber de antemano cómo funciona cada uno. Su truco: conoce una versión genérica de cada tipo (un mouse básico, una pantalla básica), y para lo especializado confía en el driver: un programa que el fabricante provee y que le enseña al SO cómo manejar ese modelo específico.

🔄 Actividad en pareja — 2 minutos

Con su compañero/a, piensen en un dispositivo que necesite driver: impresora, joystick, auriculares con micrófono, cámara web. ¿Qué parte de ese dispositivo NO funcionaría con el driver genérico del SO? Discutan.

🟢 Genérico

El SO ya lo sabe. Conectas un teclado USB y funciona: letras, números, símbolos. Sin instalar nada.

🔧 Driver específico

El fabricante lo provee. Activa lo "extra": luces RGB, macros, teclas programables, sensores de huella.

⚠️ Sin driver

Aparece el triángulo amarillo en el Administrador de Dispositivos. El dispositivo no funciona o funciona a medias.

👨‍🏫 En el aula — Administrador de Dispositivos real

El docente abre el Administrador de Dispositivos real en una PC (o en la TV):

  1. Busquen la lista gigante de dispositivos: cada uno tiene un driver cargado por el SO al iniciar.

🔍 En la vida real: Windows vs Linux vs Android

Windows depende de que el fabricante provea el driver (vía Windows Update o manualmente). Linux incluye la mayoría de drivers dentro del kernel: por eso al conectar algo "simplemente funciona" (a veces sin luces RGB, porque esas son propietarias). Android depende del fabricante del teléfono: los drivers vienen preinstalados y rara vez se actualizan salvo por una actualización del sistema.

👤 Usuarios y permisos

⏱️ 30 minutos · "Llaves, candados y grupos" — quién puede hacer qué

🦹 El villano: "No puedo borrar este archivo"

Intentas borrar un archivo y el SO te dice que no. ¿Por qué te bloquea si es tu computadora? Porque en el mundo del SO, "tú" no eres el rey absoluto: eres un usuario con un nivel de permisos. Algunos archivos pertenecen a otro usuario, al sistema, o están marcados como "solo lectura". El SO te bloquea para proteger el sistema... incluso de ti mismo.

🧠 La idea central

Si cualquiera pudiera tocar los archivos de cualquier otro, el sistema sería un caos inseguro. El SO resuelve esto con usuarios, grupos y permisos. Cada usuario tiene una identidad; cada archivo tiene un dueño; el dueño decide quién puede leer (r), escribir (w) o ejecutar (x). En un SO multiusuario, esta protección es esencial.

🔑 Los tres permisos clásicos (rwx)

👁️ r — read

Ver el contenido o listar la carpeta. Sin r, ni siquiera ves qué hay.

✏️ w — write

Modificar el archivo o añadir/eliminar en la carpeta. Sin w, es de solo lectura.

▶️ x — execute

Correr el archivo como programa o entrar a la carpeta. Sin x, una app no arranca.

👥 Los tres niveles de quién

🧑

Owner (dueño)

El usuario que creó el archivo. Tiene sus propios permisos.

👥

Group (grupo)

Un conjunto de usuarios (ej: "alumnos"). Permisos del grupo.

🌍

Others (otros)

El resto del mundo. Lo que pueden hacer los que no son dueño ni del grupo.

👨‍🏫 En el aula — Misión Hackeo de Permisos 🕵️

Aprovechando que están en parejas con una PC, el docente reta:

  1. Creen un archivo de texto en la consola (Bloc de notas → guardar como secreto.txt).
  2. Blíndenlo: en Windows attrib +r secreto.txt (solo lectura); en Linux chmod 000 secreto.txt (nadie puede leer).
  3. Reta al compañero/a de la PC vecina a que intente borrarlo. ¡No podrá! El SO se lo impedirá.
  4. "Hackeen" el permiso de vuelta: attrib -r secreto.txt o chmod 644 secreto.txt para recuperar el control.

Esto les fascina: entienden el poder real de la seguridad del SO.

🔍 En la vida real: Windows vs Linux vs Android

Windows usa ACL (listas de control de acceso): cada archivo detalla qué usuario exacto puede hacer qué. Linux usa el modelo clásico rwx (dueño/grupo/otros). Android lleva esto al extremo: cada app es su propio usuario de Linux, así que una app no puede leer los datos de otra. Por eso un virus de una app no se propaga tan fácilmente.

🧠 La idea central

💡 ¿Qué significa cada celda?

Monousuario · Monoproceso: MS-DOS. Una persona, una tarea. Multiusuario · Multiproceso: servidor Linux. Muchos usuarios, varios programas a la vez. Monousuario · Multiproceso: tu celular. Multiusuario · Monoproceso: raro hoy, algunos sistemas antiguos.
